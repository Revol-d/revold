# ADR-0012: Estratégia de testes — dados realistas, sandbox de serviço externo, e evals de agente de IA

**Status:** Aceito

## Contexto
Uma reflexão trazida pelo Samuel (baseada em prática comum de empresas maduras: Testcontainers, fábricas de dados, sandbox de API externa via HTTP, e "LLM-as-judge" para agentes de IA) foi comparada com o estado real do projeto. O ponto central — dado de teste "limpo demais" (fixture escrita à mão, sempre no formato ideal) esconde bug que só aparece com dado de produção (sujo, com acento/emoji, preço quebrado, texto vazio) — já era, em parte, a filosofia do projeto desde o planejamento inicial (ver `avaliacao-planejamento-revold.md`, seção 3.3: toda integração externa precisa de porta + adapter sandbox testável). Esta ADR formaliza o que já existia implicitamente e fecha os gaps encontrados na avaliação.

## Decisão
Quatro camadas de teste, cada uma com uma convenção de quando roda e quando pula (skip) — nenhuma delas deveria falhar o CI por falta de infraestrutura ou credencial que não é responsabilidade de quem está rodando o teste naquele momento:

1. **Unitário** (sem marker): lógica pura ou contra um fake em memória. Roda sempre, em qualquer ambiente, sem exceção.
2. **Fábricas de dados** (`factory-boy` + `Faker`, locale `pt_BR`, pacote `tools/testing` → `revold_testing`): usadas nos testes unitários/integração para gerar dado *realista* (nome com acento, preço com centavos quebrados, descrição vazia) em vez de só fixture limpa escrita à mão. Não substitui fixture manual onde o cenário exige um valor exato e legível (ex. "produto com SKU X") — complementa, principalmente em teste de edge case e em lote (N produtos gerados de uma vez contra Postgres real).
3. **Integração** (`@pytest.mark.integration`): contra infraestrutura real (Postgres+pgvector), não fake — reservado pro código mais arriscado de acertar só com fake (SQL de verdade: `ORDER BY`, `ILIKE`, `cosine_distance` do pgvector, reconciliação de variante por SKU). Pula sozinho se `DATABASE_URL`/`TEST_DATABASE_URL` não apontar pra um Postgres alcançável. Roda **também no CI** via `service` do GitHub Actions (`pgvector/pgvector:pg16`) — não só localmente; um teste de integração que só roda na máquina de quem escreveu não pega regressão de quem não sabe que precisa subir Postgres antes de rodar `pytest`.
4. **Sandbox de serviço externo** (`respx` interceptando `httpx`): todo adapter real de serviço externo (Azure OpenAI hoje; Azure AD/Google/WhatsApp Business API quando forem escritos) ganha um teste que simula a API HTTP de verdade — sem credencial real, mas exercitando o código de produção de verdade (parsing de request/response, propagação de erro como exceção específica, não string vazia engolida).
5. **Evals do assistente de IA** (`@pytest.mark.eval`, `cores/core-ai-assistant/evals/`): dividido em dois níveis, porque "qualidade de resposta de LLM" e "a orquestração está certa" são perguntas diferentes:
   - **Comportamental** (`test_behavior.py`): dataset de ~15 perguntas realistas (gíria, emoji, pergunta vazia, texto longo, cada frase-gatilho de intenção de compra) rodando contra o `FakeLLMProvider`/`FakeProductIndex` — determinístico, sem credencial, roda sempre. Testa a heurística de escalar pro WhatsApp e se a recuperação (RAG) aconteceu — não a qualidade do texto.
   - **LLM-as-judge** (`test_llm_judge.py`): usa o **mesmo** `LLMProvider` configurado (`LLM_PROVIDER`) tanto para gerar a resposta quanto para julgá-la num rubric de 0-10 (relevância, gramática, tom, resolução) — reaproveita a porta existente em vez de um cliente de avaliação à parte. Só roda de verdade com `LLM_PROVIDER=azure-openai` e credencial real configurada; pula sozinho caso contrário (mesma convenção do item 3), porque com o provider `dev` a resposta é sempre o mesmo texto de regra fixa e "avaliar a qualidade" dela não mediria nada real.

Novos comandos no `Makefile`: `make test-eval` (roda só os testes marcados `eval`). `test-unit`/`test-integration`/`test-contract` já existiam apontando pra markers que nunca tinham sido registrados nem usados — registrados agora em `pyproject.toml` (`[tool.pytest.ini_options].markers`).

## Gaps encontrados e corrigidos nesta rodada
- **O CI nunca rodava o teste de integração contra Postgres real** — ele só pulava (skip) silenciosamente por falta de `DATABASE_URL`, escondendo exatamente o tipo de bug que motivou escrevê-lo. Corrigido com o `service` do GitHub Actions.
- **`AzureOpenAIEmbeddings` fazia uma chamada de rede escondida** (via `requests`, não `httpx` — por isso passava despercebida por `respx`) pro tiktoken baixar o arquivo de encoding de um blob storage público da Microsoft na primeira chamada, só para contar/cortar tokens localmente. Numa rede com egress restrito (como o Terraform deste projeto se propõe a controlar) isso podia falhar silenciosamente em produção. Corrigido com `check_embedding_ctx_length=False` — descrição de produto é curta o bastante pra não precisar de corte local.
- **Nenhum teste existia pro `PostgresProductIndexRepository`** (índice vetorial pgvector) — nem contra fake, nem contra Postgres real. É o único lugar do repositório que usa o operador `cosine_distance` da extensão pgvector; adicionado.
- **Documentação incorreta**: o status do projeto dizia que os adapters reais de Azure AD/Google eram "código pronto, não testado". Não são — só existe o stub de desenvolvimento; os seletores reais levantam `NotImplementedError` de propósito (nem foram escritos ainda, precisam da credencial pra isso). Corrigido.

## Consequências
- Suíte de teste cresceu de 213 para 258 passando (mais 14 que pulam sem credencial Azure OpenAI), cobertura 98%, sem regressão.
- Fábricas de dados e sandbox HTTP existem como padrão a seguir para o próximo core/adapter externo — não é preciso reinventar a abordagem a cada vez.
- O eval comportamental do assistente de IA passa a ser regressão real (rodou contra 15 casos, não 6) sem custo de credencial; o eval de qualidade via LLM-as-judge fica pronto pra rodar assim que houver credencial Azure OpenAI real, sem precisar escrever nada a mais.
- Não adotado nesta rodada (fica pra quando fizer sentido, não é bloqueio técnico): estender fábricas de dados para os outros cores além de catalog; sandbox `respx` para os futuros adapters reais de Azure AD/Google assim que forem escritos.
